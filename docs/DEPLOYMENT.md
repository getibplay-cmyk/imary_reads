# نشر وتشغيل Imary Reads

## قبل التشغيل

1. استخدم خادمًا يدعم Docker Compose v2، وأشر سجل DNS للنطاق إلى الخادم. افتح 80 و443 فقط للجمهور. PostgreSQL وPHP-FPM غير منشورين على منافذ عامة في الملف المرفق.
2. انسخ `.env.production.example` إلى `.env` وأدخل `APP_URL=https://...` و`SITE_DOMAIN` دون بروتوكول، واسم قاعدة البيانات ومستخدمها وكلمة مرور قوية. لا تضع أسرارًا في المستودع.
3. أنشئ مفتاحًا مرة واحدة، وانسخه إلى `APP_KEY` في ملف البيئة:

```bash
php -r 'echo "base64:".base64_encode(random_bytes(32)).PHP_EOL;'
```

احتفظ بالمفتاح في مدير أسرار ونسخة احتياطية مشفرة. تغييره دون خطة يفقد القدرة على فك بيانات التحقق بخطوتين والجلسات المشفرة.

4. اضبط SMTP واسم المرسل وعنوانه، و`CONTACT_EMAIL`، وتحقق من SPF/DKIM/DMARC لدى مزودك. `MAIL_SCHEME=smtps` مناسب لخادم SMTPS على 465؛ استخدم إعداد مزودك الصحيح.
5. راجع صفحات الشروط والخصوصية وحقوق النشر وأدخل هوية المشغل ووسيلة الاتصال والإجراءات الملائمة لبلد التشغيل. النصوص الحالية محتوى أساسي قابل للتخصيص، وليست اعتمادًا قانونيًا.

## تشغيل الحاويات

```bash
docker compose build --pull
docker compose up -d postgres signatures
docker compose run --rm app php artisan migrate --seed --force
docker compose run --rm app php artisan imary:admin you@example.com
docker compose up -d
docker compose exec app php artisan imary:doctor --production --scan
```

Caddy يخدم مجلد `public` ويتولى HTTPS للنطاق. خدمات `app` و`worker` و`scheduler` تستخدم الصورة نفسها ومخزن الملفات الخاص المشترك. ClamAV يعمل محليًا داخل العامل، و`signatures` يحدّث قواعده. قاعدة البيانات تحفظ الجلسات والكاش وطابور المهام؛ Redis غير مطلوب لهذا الإعداد.

قد يستغرق تنزيل التواقيع الأولى وقتًا. إذا فشل الفحص يبقى الملف محجوزًا ولا يصبح متاحًا. راجع سجلات `signatures` وأعد المهمة من إدارة الملفات بعد معالجة السبب. لا تضبط ماسحًا وهميًا لإتاحة الملفات.

لا تستخدم `docker compose down -v` على بيانات حقيقية: يحذف ذلك وحدات التخزين. تثبيت الصور إلى digest ومراجعة تحديثاتها جزء من تشغيل الخادم، خاصة قبل الترقيات.

## النشر دون Docker

ثبت PHP 8.3+ وامتداداته، PostgreSQL، Composer، Node.js وClamAV. شغّل `composer install --no-dev --prefer-dist --optimize-autoloader` ثم `npm ci --ignore-scripts && npm run build`. اجعل document root هو `public` فقط، ولا تنشئ رابطًا عامًا لـ`storage/app/private`.

شغّل PHP-FPM، وعامل `php artisan queue:work --timeout=120 --tries=3` تحت مشرف عمليات، وأضف `php artisan schedule:run` إلى cron كل دقيقة. يجب أن يكون `retry_after` أطول من مهلة العامل؛ الإعداد الافتراضي 150 ثانية.

عند وجود وكيل عكسي، اضبط `TRUSTED_PROXIES` إلى عناوينه الفعلية فقط؛ لا تثق في الإنترنت كله. لا تعطل التحقق من شهادة قاعدة البيانات أو البريد. اتصالات قاعدة بعيدة تحتاج إعداد TLS المناسب، مثل `DB_SSLMODE=verify-full` وشهادة الجهة الموثوقة.

## الترقية

1. سجّل الالتزام الحالي وخذ نسخة احتياطية متزامنة للقاعدة والملفات ومفتاح التطبيق.
2. اختبر الترحيلات على نسخة معزولة، ثم ضع الخدمة في وضع الصيانة عند الحاجة.
3. ابنِ الصور الجديدة. طبّق `php artisan migrate --force`، ثم أعد تشغيل app/web/worker/scheduler على الإصدار نفسه.
4. في النشر التقليدي، نفذ `php artisan optimize` و`php artisan queue:restart`. داخل الحاويات، التخزين المؤقت محلي لكل حاوية؛ أعد بناء/تشغيل الخدمات عند تغيير البيئة، ولا تفترض أن تشغيل optimize في حاوية مؤقتة ينتقل إلى البقية.
5. شغّل doctor واختبار دخول وتحقق بريد وكتابة فصل وقراءة وتنزيل. افحص ملفات الحجر قبل إتاحة رفع الملفات للعموم.

## النسخ الاحتياطي والاستعادة

البيانات الأساسية: PostgreSQL، `storage/app/private`، `APP_KEY` وإعدادات البيئة، وأي ملفات مرتبطة بإصدارات التطبيق. استعمل نسخة خارج الخادم، مشفرة وبصلاحيات محدودة.

مثال لنسخة قاعدة البيانات إلى مسار خاص:

```bash
umask 077
docker compose exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > imary-database.dump
docker compose exec -T app tar -C /var/www/html/storage/app -czf - private > imary-private-files.tar.gz
```

هذه الأرشيفات غير مشفرة بذاتها. شفّرها بأداة النسخ الاحتياطي المعتمدة لديك قبل نقلها. إن احتجت اتساقًا دقيقًا بين الملفات والقاعدة، أوقف الكتابة وعامل الطابور مؤقتًا أثناء اللقطة. لا تضمّن ملفات البيئة في أرشيف عام.

اختبر `pg_restore` واستخراج الملفات على قاعدة ومخزن جديدين منفصلين، باستخدام مفتاح التطبيق المطابق، ثم افحص الحسابات والفصول والملفات. لا تنفذ restore فوق الإنتاج قبل مراجعة الوجهة. اختبارات الاستعادة الحقيقية لم تُنفذ في جلسة الإنشاء.

## المراقبة

- `/up` يختبر إقلاع التطبيق؛ `imary:doctor --production --scan` يتحقق أيضًا من القاعدة والإعدادات وماسح الملفات.
- راقب الأخطاء، مساحة التخزين، المهام الفاشلة (`php artisan queue:failed`)، تأخر الطابور، تواقيع ClamAV، الشهادة، وزمن الاستجابة. اجعل إشعارات المراقبة تصل إلى المشغل.
- الفصل المنشور مستقبلًا يظهر عند موعده؛ مهمة الإشعارات تعمل عبر المجدول وتمنع التكرار بعلامة `notified_at` وقفل قاعدة البيانات.
- سجلات المشاهدات هي زيارات يومية لكل حساب/جلسة، وليست ضمانًا لعدد الأشخاص الفريدين.
- اختبر قارئ الكتاب على هاتف فعلي وحاسوب باللغات الثلاث، مع التكبير ولوحة المفاتيح، قبل الإطلاق العام.
